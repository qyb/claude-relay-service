# CRS Prompt 落盘脱敏设计（Prompt Masking）

本文档描述 CRS 在 prompt log（见 `PROMPT_LOG.md`）落盘前对敏感内容进行脱敏的设计。

Prompt log 的首要用途是工作审计（按员工/session 还原真实用户输入），脱敏必须在不破坏这一用途的前提下，阻断密钥与 PII 进入日志文件。

## 一、背景：7 天生产数据的验证

对 2026-08-08 ~ 2026-08-14 prompt log 的敏感模式扫描，确认了以下真实泄露：

| 类型 | 实例（脱敏转写） | 出现情况 |
|---|---|---|
| 数据库连接串含密码 | `password=Leon;persistsecurityinfo=True;...` | 王新旺，2 次 |
| 硬编码密钥源码 | `SECRET_KEY = 'hardcoded...'` | 杨凡，42 次 secret 模式命中 |
| 认证头 | `Authorization: Bearer ...`、`password: 'Set...'` | 李博等 |
| 客户手机号 | `1[3-9]\d{9}` 全明文 | 李博 38、杨凡 21、王新旺 14 等 |
| 客户邮箱与邮件原文 | 收件人地址、`.eml` 内容 | 陈洋排障会话 |
| 生产环境信息 | 内网 IP（李博 31 次）、内部域名（`git.sendcloud.io` 等）、nginx 访问日志 | 多人 |

Prompt log 因此成为一份"结构化的公司敏感信息汇编"：无人 review、全文明文、随日志文件下载流转。脱敏必须在写入磁盘**之前**完成，事后清理不可依赖（日志已被下载、备份）。

## 二、目标与非目标

### 2.1 目标

- 密钥类（密码、token、API key、私钥、连接串中的凭据）落盘前自动替换，不可恢复。
- PII（手机号、邮箱）自动 mask。
- 替换后保留**可关联性**：同一密钥多次出现可识别为同一个（用于审计追查"泄露范围"）。
- 规则可热更新、有版本号，规则命中情况可统计。

### 2.2 非目标

- 不追求语义级理解（不判断"这段代码是 auth 逻辑所以豁免"）。
- 不做对账/告警（本设计只管落盘管道；对 mask 命中率的监控由消费端基于 `mask_count` 统计）。
- 不处理 prompt 之外的链路：telemetry 已承诺不落正文；上游请求体不受本设计影响。
- 不保证零漏报：无结构特征的高熵串只标记不替换（见 3.4），人工复核兜底。

## 三、匹配规则设计

核心原则：**用"结构（词 + 赋值符号）+ 值形状"代替"关键词 + 前后窗口"**。

理由：

- "key/password/密钥"等关键词在日常 prompt 中高频出现（`api key`、`key_name`、密钥机制讨论），按词触发窗口 mask 会大量误伤，破坏审计用途。
- 密钥的可靠特征是赋值结构（`password=值`、`"token": "值"`）或值本身的形状（`sk-` 前缀、JWT 的 `eyJ` 头、PEM 块），而非附近有某个词。
- 固定 N 字符窗口对长值（JWT 数百字符、PEM 块上千字符）必然漏 mask。

### 3.1 第 1 层：结构锚点（自动 mask）

```
(password|passwd|pwd|secret|secret_key|token|apikey|api_key|access_key|
 密码|口令|密钥|凭据)
\s*[=:：]\s*
```

捕获后续值直到边界（成对引号、分号、空白、换行、JSON 逗号）。

- 命中实例：`password=Leon;persistsecurityinfo=True`、`SECRET_KEY = 'hardcoded...'`、`"password": "Set..."`。
- 值为空、占位符（`***`、`<password>`、`xxx`、`your_password`）或纯语言描述（`密码忘记了吧`）不替换。

### 3.2 第 2 层：值形状（自动 mask）

| 模式 | 说明 |
|---|---|
| `sk-[A-Za-z0-9]{16,}`、`AKID[A-Za-z0-9]+`、`ghp_[A-Za-z0-9]+` 等供应商前缀 | 逐供应商维护前缀清单 |
| `eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]+\.` | JWT（base64 头部特征） |
| `-----BEGIN [A-Z ]*PRIVATE KEY-----[\s\S]*?-----END ...-----` | PEM 私钥整块 |
| `(mysql|postgres(ql)?|mongodb|redis|jdbc[^\s:]*)://[^\s/:]+:[^\s/@]+@` | 连接串中的 `user:pass@` |
| `Bearer\s+[A-Za-z0-9._-]{20,}`、`Authorization:?\s*\S+\s+[A-Za-z0-9._-]{20,}` | 认证头 |
| `[A-Fa-f0-9]{32}|[A-Fa-f0-9]{40}|[A-Fa-f0-9]{64}` 且上下文非颜色值/commit hash | 常见 digest 形态（保守启用，规则集可关） |

### 3.3 第 3 层：PII（自动 mask）

- 手机号：`1[3-9]\d{9}`（含 `+86` 前缀形态），保留前 3 后 2：`135****23`。
- 邮箱：本地部分保留首字符：`h***@qq.com`。
- 身份证：`\d{17}[\dXx]`，同手机号策略。

PII 采用部分 mask 而非全替换：排障场景（"这个手机号 135****23 收不到短信"）仍保留可读性，与"客户手机号全明文进日志"之间取平衡。

### 3.4 第 4 层：高熵检测（只标记，不替换）

连续字符串满足：长度 ≥ 20、字符集 ≥ 3 类（大小写/数字/符号）、Shannon 熵 ≥ 4.5。

- **不自动替换**：误报不可控（base64 图片数据、正常 hash、压缩串都会命中），自动 mask 会重创日志可读性。
- 处理方式：日志行增加 `suspected_secret: true` 元字段，供人工/离线复核。复核确认的新模式沉淀回第 2 层规则。

## 四、替换格式与指纹

```
[MASKED:{类型}:{hmac8}]
```

- `hmac8` = HMAC-SHA256(原始值, 服务端脱敏密钥) 的前 8 个 hex 字符。
- PII 用部分 mask，不用指纹；密钥类用指纹全替换。

示例：

```
原始: password=Leon;persistsecurityinfo=True
落盘: password=[MASKED:password:h3f9a2c1];persistsecurityinfo=True
```

特性：

- **不可逆**：日志文件不含原值，HMAC 密钥仅存于服务端配置。
- **可关联**：同一密钥在不同 prompt 中指纹一致，可回答"该密码共出现在多少条 prompt、哪些员工 session"——审计追查泄露范围的关键能力。
- **防撞库**：与简单 hash 不同，攻击者无法对候选密码清单做离线字典比对（无 HMAC 密钥）。

## 五、元字段

每条 prompt log JSON 行增加：

| 字段 | 说明 |
|---|---|
| `mask_version` | 规则集版本号（如 `2026.08.14`），规则热更新后新行带新版本 |
| `mask_count` | 本条 prompt 的自动替换次数（不含 suspected 标记），不含任何内容 |
| `suspected_secret` | 高熵层命中时为 `true`，否则省略 |

这些字段支持：统计规则命中分布、对比版本间误报率变化、圈定需人工复核的日志行，且本身不泄露信息。

## 六、实现要点

1. **管道位置**：prompt 观测回调内、写文件前的最后一步。title-gen 的 `<session>` 包装 prompt（含对话摘要）走同一条管道。
2. **单趟执行**：各层规则合并为一次扫描，长匹配优先（PEM 块先于行级规则），记录已替换区间避免重叠规则二次处理。
3. **规则外置**：规则集（正则 + 类型 + 是否自动）放配置或独立规则文件，支持热加载；新增供应商密钥前缀不需要发版。
4. **性能**：prompt 中位长度数百字节、p99 数十 KB，单趟正则开销可忽略；对超长 prompt（> 1MB）设置处理上限，超出部分整体走高熵标记路径。
5. **服务端脱敏密钥**：HMAC 密钥与 API Key 加密密钥同等级管理，轮换时指纹不可比（接受；日志按保留期滚动，跨期关联非刚需）。

## 七、回归测试集

以 2026-08-08 ~ 08-14 真实日志建立 golden 测试集：

**必须命中（召回）**：

- `password=Leon;persistsecurityinfo=True;...`（连接串）
- `SECRET_KEY = 'hardcoded...'`（代码赋值）
- `Authorization: Bearer ...`、`password: 'Set...'`（认证头/ YAML 值）
- 客户手机号（`1[3-9]\d{9}` 明文）
- 收件人邮箱明文

**必须不命中（精度）**：

- "通行证管理 角色管理 的管理二字可以去掉"（日常中文讨论）
- `api key 记录`、`key_name`、`sticky_session` 等产品术语
- "后台无 token 降级 admin 很危险"（安全讨论，无值）
- commit hash、颜色值等 digest 形态的正常使用

每次规则变更跑测试集，召回与精度双指标不回退方可发布。

## 八、实施顺序

1. **P0**：第 1、2 层规则 + 指纹替换 + `mask_version`/`mask_count` 字段上线（阻断真实泄露的主要来源）。
2. **P0**：第 3 层 PII mask。
3. **P1**：第 4 层高熵标记 + `suspected_secret` 字段。
4. **P1**：基于真实日志的误报复盘一轮，调优第 2 层保守规则（digest 形态默认关闭，视误报开启）。
5. **P2**：管理台展示 mask 命中统计与待复核列表。

## 九、边界与已知限制

- 已落盘的历史日志不受影响，需另行一次性清理/收紧导出权限（独立工作项）。
- 图片 base64、长 hash 与真实密钥在高熵层不可区分，依赖人工复核闭环。
- 结构锚点依赖 `=`/`:`/`：` 赋值形态，"密码是 Leon 这样吧"这类自然语言披露不命中——属于工作审计本身会发现的行为，不作为自动规则目标。
